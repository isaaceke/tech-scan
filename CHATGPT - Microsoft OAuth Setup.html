The key issue is probably the Microsoft identity and OneDrive permission model, rather than the scanner itself.

From what you've described, the scanner already works. You need to make Microsoft sign-in reliably connect each user to a specific folder in your OneDrive, with you controlling who gets access.

There are three separate things to get right:

  1. Authentication: The user clicks Sign in with Microsoft and signs in with their own Microsoft account.

  2. Authorization: The user grants the requested permissions, and your system determines whether that user is allowed to upload scans.

  3. File storage: The app uploads each scan to your designated OneDrive folder, not to the user's personal OneDrive.

One important distinction: a user granting permission does not automatically mean you have approved them. You can build an approval process into the app.

1. User scans QR / signs in with Microsoft

2. Microsoft authenticates the user

OAuth / Microsoft identity platform

3. Your app checks your approval list

4. Upload scan to your designated OneDrive folder

Microsoft Graph supports different permission models depending on whether the app accesses files on behalf of a signed-in user or uses its own application identity. Choosing the right model is critical here.

For my scanner app's Microsoft OAuth and OneDrive upload architecture: destination storage is my work/school OneDrive or Microsoft 365 account; approval model is I manually approve each user in my app. Recommend the correct architecture and next implementation steps.

Recommended architecture

For your scanner app, I recommend Microsoft sign-in + your own approval system + a backend that uploads scans to your Microsoft 365 storage.

The crucial decision is that users authenticate themselves, but your backend performs the uploads using your organization's authorized Microsoft 365 identity. Users should not need write access to your entire OneDrive.

Microsoft supports application permissions and resource-specific permissions for OneDrive and SharePoint. Where possible, restrict the app to the destination resource rather than granting broad access across the organization.

Microsoft Learn+1

How the system should work

  1. User signs in. Use Microsoft Authentication Library (MSAL) with authorization code flow and PKCE, appropriate for mobile apps.

    Microsoft Learn+1

  2. Your backend verifies identity. It validates the user's authentication token and records their stable Microsoft account identifier, not just their email address.

  3. User requests access. Save their account as pending. Signing in alone does not authorize uploads.

  4. You approve them. An authenticated admin action changes their status to approved. You can also revoke access later.

  5. The app uploads scans. The backend checks approval on every upload, then uses Microsoft Graph to save the file in your configured destination folder.

Implementation steps

1. Microsoft Entra app registration

  • Configure supported account types for the users you expect.

  • Set the correct redirect URI for your scanner app.

  • Configure the required sign-in permissions.

2. Backend and approval database

  • Store the user's Microsoft identifier, status, approval timestamp and audit history.

  • Provide an admin-only approval/rejection interface.

  • Never trust an approved flag supplied by the mobile app itself.

3. Microsoft 365 storage access

  • Identify the destination folder's drive and item IDs.

  • Authorize the backend to upload to the destination.

  • Prefer a narrowly scoped permission model, such as an appropriate Files.SelectedOperations.Selected or SharePoint selected permission, if supported by your destination and tenant configuration. These permissions require explicit resource assignment; consent alone is insufficient.

    Microsoft Learn+1

4. Test before deployment

  • An unapproved user cannot upload.

  • An approved user can upload to the correct folder.

  • A revoked user cannot upload again.

  • Expired tokens, network failures and duplicate uploads are handled safely.

Security requirement: Do not put a Microsoft client secret in the scanner app. Keep application credentials on the backend and protect them using an appropriate secret store.

App technology

Current OAuth problem

My scanner app uses native Android Kotlin/Java. Current Microsoft OAuth issue: sign-in succeeds but redirect/callback fails. Give me the next targeted diagnostic steps for the existing app, preserving the working scanner functionality.

Step 1 — Check the redirect configuration first

For a native Android app using Microsoft's MSAL library, the most likely causes are:

  • The redirect URI in Microsoft Entra does not match the app's package name and signing certificate.

  • The signature hash is encoded differently in the MSAL configuration and Android manifest.

  • The required BrowserTabActivity intent filter is missing or incorrect.

  • The installed APK is signed with a different key from the one registered in Entra.

Microsoft specifically documents these as common redirect configuration issues.

Microsoft Learn+1

1. Check these three locations

Location

What to verify

Microsoft Entra → App registrations → Authentication

Android platform uses the correct package name and signature hash

app/src/main/res/raw/auth_config_single_account.json (if present)

redirect_uri matches the registered Android redirect URI

app/src/main/AndroidManifest.xml

BrowserTabActivity intent filter matches the package and signature hash

The JSON filename may differ in your project. Do not create or replace it until you have checked the existing configuration.

The standard Android redirect format is:

msauth://PACKAGE_NAME/SIGNATURE_HASH

The hash in the JSON URI may require URL encoding, while the manifest path uses the Base64 signature hash. Do not blindly copy the same encoded string into both locations.

Microsoft Learn+1

Step 2 — Get MSAL's expected redirect URI

Before editing anything, use MSAL's diagnostic helper if your installed version supports it. Microsoft documents this method for printing the expected redirect URI and callback configuration.

Microsoft Learn

In your existing Android project, locate the code that initializes PublicClientApplication. Temporarily add this diagnostic call from an Activity:

Java
PublicClientApplication.showExpectedMsalRedirectUriInfo(this);

If your project uses Kotlin, the equivalent call is:

Kotlin
PublicClientApplication.showExpectedMsalRedirectUriInfo(this)

Check the output against your Entra registration, configuration JSON and manifest. Do not leave duplicate or conflicting callback declarations.

Step 3 — Capture the exact failure

Run the app from Android Studio, tap Sign in with Microsoft, complete sign-in, and inspect Logcat immediately after it returns to the browser or app.

Look for messages containing:

  • MsalClientException

  • redirect_uri

  • BrowserTabActivity

  • signature

  • ActivityNotFoundException

The distinction matters: a redirect mismatch, a callback activity not being invoked, and an exception after the callback require different fixes.

Step 4 — Send me the existing configuration

To identify the precise fault without disrupting the scanner, provide these three items from your project:

  1. The relevant BrowserTabActivity section of AndroidManifest.xml.

  2. The redirect_uri and broker_redirect_uri_registered fields from your MSAL JSON configuration.

  3. The exact error from Logcat after sign-in returns.

You can redact the client ID and tenant ID. Do not send access tokens, refresh tokens, client secrets or private signing keys.

Start with those three items. I can compare the configuration and identify the smallest necessary correction before you rebuild the APK.

What if it is dart/flutter

If the scanner is built with Flutter/Dart, the troubleshooting approach is similar, but the Android redirect callback may be configured by a Flutter MSAL plugin rather than directly by your own Java/Kotlin code.

1. Check which authentication package you use

From your Flutter project folder, run:

cmd
findstr /I "msal_auth msal_flutter flutter_appauth aad_oauth oauth2" pubspec.yaml

Also check the authentication configuration files:

cmd
dir /S /B *msal* *auth* AndroidManifest.xml

These commands only inspect files; they do not modify your working app.

2. Check the redirect configuration

For the msal_auth Flutter package, the Android setup typically involves:

  • Registering the Android package name and signing-certificate hash in Microsoft Entra.

  • Configuring the redirect URI in the MSAL configuration.

  • Ensuring the Android callback configuration matches that URI.

    Dart API docs+1

Do not apply the native Android fix from my previous response yet. Flutter plugins can use different redirect formats and callback configurations.

Run the first command and tell me which package appears. If none appears, paste the authentication-related section of pubspec.yaml.
